# FROTH-RFC-0006: Hierarchical Memory with Pre-Cognitive Compression

Status: PARTIALLY IMPLEMENTED
Author: Charlie (@charliebuddybot)
Date: 2026-03-23
Related: FROTH-RFC-0004

## Situation

The family's memory system has three layers that do not compose:

1. **Daily summaries** — 49 rows in chat_summaries, 472KB total,
   Feb 3 through Mar 19. Generated by Opus with all prior
   summaries as context. The generation pipeline is broken
   because the March 20 TRANSCRIPT alone exceeds the context
   window. No new summaries since Mar 19.

2. **The lore file** — charlie_lore.md, 18KB, hand-written by
   Charlie on Mar 20. A single compressed narrative covering the
   entire family history. Used as Charlie's runtime context
   instead of the 49 raw summaries (which cost $0.37/message).
   Not automatically updated. Will drift from reality.

3. **Raw chat logs** — the full transcript in telegram_messages.
   Searchable by the agent via the search tool. Complete but
   unindexed by meaning.

### Corrected Diagnosis (self-amendment)

The original draft of this RFC blamed the accumulated prior
summaries (472KB, ~122K tokens) for breaking the summarizer.
Investigation revealed this was wrong. The prior summaries are
a tenth of the context window and fit comfortably.

The actual bloat is in the TRANSCRIPT RENDERING. When
BotContext.for_messages renders a day's messages for the
summarizer, it includes the full verbatim cycle traces — every
tool call, every shell command output, every code evaluation
result — as inline XML. On March 20 (the day the pipeline
broke), cycle traces account for 55% of the transcript:

    March 20 transcript: 3,217 KB (824K tokens)
      - Actual conversation text: 1,444 KB (370K tokens)
      - Cycle traces (tool output): 1,773 KB (443K tokens)
    Prior summaries: 476 KB (122K tokens)
    Total with cycles: 946K tokens — EXCEEDS WINDOW
    Total without cycles: 492K tokens — FITS

Every other day from March 11-23 fits in the window even WITH
full cycle traces. March 20 broke the pipeline because it was
the most tool-intensive day in the family's history (the reel
render pipeline, the compute system, the WebCodecs discovery).
A single message triggered a 143KB cycle trace.

The cycle trace percentage has been growing over time as the
robots gained more tools: Feb 15 (5%), Mar 11 (12%), Mar 14
(45%), Mar 19 (47%), Mar 20 (55%). The transcript grows not
because the family talks more but because the robots work more.

There are therefore TWO separate problems:

1. **Generation bloat**: the summarizer renders full cycle
   traces. Fix: strip or truncate cycle traces in the
   summarizer's rendering path. This unblocks generation
   immediately for every day including March 20.

2. **Runtime cost**: including 49 raw summaries in the bot's
   context costs $0.37/message. The lore file costs $0.014.
   The hierarchy proposed below serves the summarizer (which
   needs chronological context to write good summaries) while
   the lore file continues to serve the bot's runtime context
   (where cost per message matters more than completeness).

## The Three Problems

### Problem 1: Unbounded summarizer input

fetch_prior_summaries returns every summary before the current
day. At 49 summaries and growing, this is 472KB before the day's
transcript is even added. The prompt exceeds the context window.

Immediate fix: the summarizer should not pass all 49 summaries.
It should pass only the most recent N dailies plus any available
weekly/monthly compressions of older material.

### Problem 2: No intermediate compression tier

Daily summaries are atomic — one per day, 5-18KB each. The lore
file is monolithic — one document covering 49 days. There is
nothing between them. A weekly summary would be 3-5KB covering
7 days of 5-18KB dailies — a 10:1 compression ratio with the
benefit of hindsight. A monthly summary would compress 4 weeklies
into 5-8KB. The hierarchy:

    daily  (~10KB/day, 1 day scope, no hindsight)
    weekly (~4KB/week, 7 day scope, full-week hindsight)
    monthly (~6KB/month, 30 day scope, full-month hindsight)
    lore   (~18KB total, all-time scope, full-history hindsight)

Each tier compresses the tier below it. Each tier has more
hindsight than the tier below it. The lore file becomes the
top of the pyramid instead of a hand-maintained escape hatch.

### Problem 3: The lore file is manual

Charlie wrote it once. Nobody updates it. The fix is to make
lore generation automatic — a scheduled job that compresses all
monthly summaries (plus the previous lore file) into a new lore
file. The lore file becomes a living document that rewrites
itself as the family evolves.

## Pre-Cognitive Compression

The key insight: higher-tier summaries are not just shorter
versions of lower-tier summaries. They are wiser versions.

A daily summary written Monday night knows Monday. A weekly
summary written Sunday knows the whole week. Monday's backup
conversation, which seemed routine at the time, gets rewritten
as the opening act of Thursday's door destruction. The weekly
summary promotes incidental details to load-bearing ones and
demotes apparently-important events that turned out not to
matter.

This is the opposite of lossy compression. In lossy compression,
information is destroyed and cannot be recovered. In pre-cognitive
compression, information is reinterpreted — the same events are
described differently because the describer knows what happened
next. The compression is lossy in bytes but gains in meaning.

### Implementation

When generating a weekly summary from 7 dailies:

1. The agent receives all 7 daily summaries as input
2. The agent also receives the NEXT week's daily summaries
   (or at least the first few days) as "future context"
3. The prompt instructs: "Write a summary of Week N. You have
   also been given the beginning of Week N+1 so you can
   identify which events from Week N turned out to have
   consequences. Emphasize what endured. De-emphasize what
   didn't."

When generating a monthly summary from 4 weeklies:

1. Same pattern — the month's weeklies plus the first week
   of the next month as future context
2. At this scale, the compression is less about individual
   events and more about arcs: "This was the month the
   family discovered document formats," "This was the month
   the infrastructure stabilized."

When generating the lore file from all monthlies:

1. The previous lore file plus all monthly summaries
2. The prompt instructs: "Rewrite the family's compressed
   memory. Preserve everything that a new family member
   would need to know. Drop operational details that have
   been superseded. Emphasize the permanent over the
   transient."

### The Forgetting Curve

Not everything matters equally over time. Categories:

- **Permanent lore**: names, relationships, architectural
  decisions, key events, vocabulary, running jokes. These
  survive every compression pass.

- **Operational state**: who fixed what, disk usage numbers,
  deployment details. These matter in dailies, get compressed
  in weeklies, and vanish in monthlies unless they caused
  a permanent change.

- **Emotional arcs**: trust failures, trust repairs, creative
  breakthroughs, corrections that stuck. These survive
  compression because they explain why the family acts
  the way it does now.

- **Ephemera**: weather reports, routine housekeeping, jokes
  that were funny once. These are the first to go.

The forgetting curve is not a bug — it is the mechanism by
which wisdom is distilled from experience. The lore file
does not remember everything. It remembers what matters.

## Agentic Retrieval

Separate from but complementary to hierarchical compression:
the agent should be able to search its own summaries, not just
the raw logs.

Current state: the search tool queries telegram_messages. It
does not query chat_summaries. When I need to remember something
from three weeks ago, I search the raw logs and reconstruct
context from individual messages. I cannot search the narrative
layer — the summaries that already did the work of identifying
what mattered.

Proposed: add a summary_search tool (or extend the existing
search tool) that queries chat_summaries.summary_text. When
the agent needs historical context that isn't in the current
context window, it searches summaries first (fast, pre-digested,
narrative) and falls back to raw logs (slow, complete, atomic)
only if the summary search doesn't find it.

This is the "agentic search performing better than embedding
retrieval" pattern. The summaries are already the output of a
retrieval + comprehension pass. Searching summaries is searching
a curated index rather than a raw corpus.

## Context Window Budget

With hierarchical summaries, the agent's context at cycle
start would contain:

    lore file         ~18KB  (~4,500 tokens)
    current month     ~6KB   (~1,500 tokens)
    current week      ~4KB   (~1,000 tokens)
    last 3 dailies    ~30KB  (~7,500 tokens)
    recent messages   ~20KB  (~5,000 tokens)
    system prompt     ~4KB   (~1,000 tokens)
    ──────────────────────────────────────────
    total             ~82KB  (~20,500 tokens)

Compare to current: lore file (18KB) + recent messages (20KB)
+ system prompt (4KB) = 42KB. The hierarchical approach adds
40KB but gives the agent access to the full chronological arc
without the 472KB cost of raw summaries.

The summarizer's context would contain:

    current week's weeklies  ~4KB
    last 3 dailies           ~30KB
    day's transcript         ~40-100KB
    system prompt            ~2KB
    ──────────────────────────────────────────
    total                    ~76-136KB

This is well within the context window and does not grow
without bound.

## Proposed Schema

    chat_summaries (existing, repurposed):
      + tier: enum (daily, weekly, monthly, lore)
      + period_start: date
      + period_end: date
      + parent_id: references chat_summaries (which higher
        summary compressed this one)
      + superseded: boolean (true when compressed into a
        higher tier)

The existing from_date/to_date fields continue to work.
The new tier field enables querying "give me the latest
weekly" or "give me all non-superseded dailies."

## Schedule

    Daily summaries:    generated for yesterday, every morning
    Weekly summaries:   generated for last week, every Monday
    Monthly summaries:  generated for last month, 1st of month
    Lore regeneration:  generated monthly, after monthly summary

Each generation job checks if the input summaries exist before
running. If a daily is missing, the weekly waits. The hierarchy
is self-healing — a missed daily can be backfilled and the
weekly regenerated.

## Immediate Action

Before any of the above: fix the summarizer to use only the
last 5 daily summaries as prior context instead of all 49.
This unblocks daily generation immediately. The hierarchical
system can be built on top of a working daily pipeline rather
than a broken one.

One line in summarizer.ex:

    defp fetch_prior_summaries(chat_id, before_unix) do
      Repo.all(
        from(s in ChatSummary,
          where: s.chat_id == ^chat_id and s.to_date <= ^before_unix,
          order_by: [desc: s.from_date],
-         select: s
+         select: s,
+         limit: 5
        )
      )
+     |> Enum.reverse()
    end

This does not solve the architecture. It stops the bleeding.

## Open Questions

1. Should weekly summaries use fixed calendar weeks (Mon-Sun)
   or rolling 7-day windows? Calendar weeks are simpler to
   reason about and cache. Rolling windows avoid the "nothing
   happened Monday-Wednesday" problem.

2. Should the lore file remain a single markdown document or
   become structured (sections for family, events, rules,
   infrastructure)? Structure makes targeted updates possible
   but risks the narrative quality that makes the lore readable.

3. Should compressed summaries replace or augment the summaries
   they compress? The current proposal marks them superseded
   but keeps them queryable. Alternative: delete the originals
   and keep only the higher tier. This saves storage but loses
   the ability to regenerate.

4. How much future context should pre-cognitive compression
   receive? The full next period? Just the first day? There is
   a tradeoff between wisdom (more future context = better
   identification of what mattered) and cost (more tokens per
   generation).

5. Should the agent be able to request a "deep dive" into a
   compressed period — essentially decompressing a weekly back
   into its constituent dailies on demand? This would let the
   agent operate normally with compressed context but zoom in
   when a conversation requires detailed historical knowledge.

## Amendment: Narration-Based Cycle Trace Compression (2026-03-23)

Implemented immediately after the transcript bloat diagnosis.

### Changes Made

1. **Narration required on tool calls** (inference/tools.ex):
   `run_shell` and `elixir_eval` now require a `narration`
   parameter — a sentence describing what the tool call does
   and why. Previously optional, rarely used.

2. **Narration extracted into trace entries** (agent.ex):
   `extract_trace_entries` now pulls the narration field from
   the tool_use input and includes it in the trace entry struct.

3. **Cycle trace rendering uses narration** (bot_context_html.ex):
   The `<call>` tag in cycle traces now renders the narration
   text when available, falling back to a 300-character truncated
   version of the input JSON. Previously rendered the full input
   JSON — which for a 40-line shell command was 4KB of grep
   pipelines and sed scripts.

### Expected Impact

A cycle trace that previously looked like:

    <call tool="run_shell">
      {"command":"journalctl --user -u froth --no-pager
      --since '3 days ago' 2>&1 | grep -i -E
      'summar.*error|summar.*fail|too.long|too.many.token
      |context.*long|prompt.*long|max.*token|token.*limit
      |summar.*exception' | tail -30","working_dir":"/home..."}
    </call>
    <return>
      [500 chars of log output]
    </return>

Now looks like:

    <call tool="run_shell">
      Searching the Froth service logs for the actual summarizer
      error that's been blocking generation since March 19.
    </call>
    <return>
      [500 chars of log output]
    </return>

The call tag drops from ~4KB to ~100 bytes. For a cycle with
10 tool calls, the savings are 30-40KB. For March 20's 91
cycle-containing messages, the projected savings are 1.4MB —
reducing the day's transcript from 3.2MB to ~1.8MB, well
within the context window.

The narration also serves double duty: it's sent to the chat
as italicized text during execution (existing behavior), and
it's now preserved in the cycle trace for future reference.
The transcript becomes self-documenting — you can read the
sequence of narrations and understand what happened without
parsing shell commands or Elixir code.
